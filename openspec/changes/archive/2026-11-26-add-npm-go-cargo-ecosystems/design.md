# Design

## Context

The MVP's engine, SDK and dependency plugin set are check-agnostic and ecosystem-agnostic. Adding an ecosystem means adding a plugin that implements `sdk.Ecosystem`, produces the `dependency-graph` fact, implements `deps.VersionRegistry` and `sdk.RemediationRealizer`, and registers in `plugins/all`.

The new ecosystems differ from the MVP's in two ways:
- npm, Yarn, pnpm and Cargo commit complete lockfiles.
- Their manifests are not enough to express a fix: the lockfile must be regenerated by the package manager.

## Goals / Non-Goals

**Goals:**
- Same user experience as the MVP ecosystems: detection, full transitive graph, updates, vulnerability fixes, verification.
- Scanning a project with a committed lockfile needs no Node.js or Rust toolchain.
- No change to engine or core SDK contracts.

**Non-Goals:**
- Bun and Deno lockfiles, Go workspaces (`go.work`) as one project, Cargo git dependencies as graph nodes or update targets (they are treated like path dependencies).
- Package-level reachability for Go (as `govulncheck` does). The graph is module-level.
- Updating a Go module across major versions (import path changes).

## Decisions

### D1. Lockfiles are the graph source for npm, Yarn, pnpm and Cargo
A lockfile is written by the package manager and records exactly what it resolved, so it meets the MVP rule that versions must match the build tool's resolution. Parsing it is fast, deterministic and works offline.
- npm: `packages` map (v2/v3), node_modules lookup to resolve edges; `dependencies` tree (v1).
- Yarn v1: its own line format. Yarn Berry and pnpm: YAML (`gopkg.in/yaml.v3`).
- Cargo: TOML (`github.com/BurntSushi/toml`, MIT).

When no lockfile is committed, the package manager generates one in lockfile-only mode (`npm install --package-lock-only`, `pnpm install --lockfile-only`, `yarn install --mode=update-lockfile`, `cargo generate-lockfile`). The plugin reads it and removes it.
*Alternative: `npm ls --json` and `cargo metadata`.* Rejected: they need the toolchain for every scan and `npm ls` needs installed `node_modules`.

### D2. Go uses the toolchain
`go.mod` does not record the module graph. `go list -m -json all` gives the selected versions, the main module, `Indirect` flags and replacements, and `go mod graph` gives the edges. Edges are mapped onto selected versions, and pseudo-entries `go@…` and `toolchain@…` are dropped. `golang.org/x/mod` (BSD-3-Clause) provides module path escaping for the proxy and `go.mod` parsing to detect `replace` and vendoring.

### D3. Fixes run the package manager in the scratch copy
`RemediationRealizer.Realize` receives the scratch workspace. The new realizers:
1. make their own text edits to manifests (`package.json`, `Cargo.toml`);
2. run the package manager in the scratch directory;
3. read the changed files, restore the originals, and return text edits (manifest edits plus full-file replacements of lockfiles and `go.sum`).

The engine then applies and verifies them as usual. A shared helper in `pkg/sdk/deps` does the snapshot, run, diff and restore. This keeps the engine contract unchanged and the verification path identical for all ecosystems.

Package managers run without lifecycle scripts (`--ignore-scripts`). Yarn classic has no lockfile-only mode, so it installs into the scratch copy, which is deleted afterwards.

### D4. Versions
`osv-scalibr/semantic` already implements the `npm`, `Go` and `crates.io` comparators OSV uses. Go versions are kept in canonical form with a leading `v` (OSV ranges omit it, so parsing adds it). Prereleases are detected by SemVer rules for all three ecosystems.

### D5. Graph path search
JavaScript graphs have thousands of nodes and many shared subtrees, so enumerating all paths (the MVP's `DirectAncestors`) is exponential. `Paths` now enumerates chains best-first: the exact distance of every ancestor to the target is computed once by reverse breadth-first search and used as the heuristic, so only partial chains that can still reach the target are explored, shortest first, up to the limit (at most 10000 without one). `DirectAncestors` uses reverse reachability. Results are unchanged for the MVP ecosystems' graphs.

### D6. Manifest edits
- `package.json` edits are byte-range replacements located by a small JSON scanner. New `overrides`, `resolutions` or `pnpm.overrides` objects are inserted with the file's indentation.
- `Cargo.toml` requirements are found in `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]`, `[target.*.…]`, `[workspace.dependencies]` and dotted tables (`[dependencies.serde]`). Inline tables and plain strings are both handled.
- Cargo requirement matching (caret by default, `~`, `=`, comparators, wildcards) decides whether a lockfile-only update is enough.

### D7. Registries
- npm: abbreviated packuments (`application/vnd.npm.install-v1+json`), scoped registries, bearer or basic auth.
- Go: `<proxy>/<escaped path>/@v/list`, falling through the `GOPROXY` list on 404/410. `direct` and `off` entries end the list.
- Cargo: sparse index files (`<index>/<prefix>/<name>`), newline-delimited JSON, `yanked` filter.

All registries use the shared HTTP cache, retries on 5xx, and return `deps.ErrPackageNotFound` when no registry knows the package.

### D8. Plugin IDs and layout
`npm`, `go` and `cargo` under `plugins/ecosystem/{npm,golang,cargo}`. Each has a `domain` package with pure parsing and editing logic, like the MVP ecosystems.

## Risks / Trade-offs

- Lockfile formats evolve → unknown versions fail with a clear message, and tests use lockfiles recorded from real package managers.
- Yarn classic `resolutions` cannot target one version → a manual change if several majors exist.
- Running package managers during fixes contacts registries → the same trust and credentials as the project's CI build; secrets are masked by the toolchain.
- `go list -m all` includes modules that are not built, so some Go findings are not reachable → documented. Teams that need reachability can add `govulncheck` through an integration.
